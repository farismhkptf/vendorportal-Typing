Medical Appointment Scheduling Status Algorithm

Programmer-Facing Final Handoff Document

⸻

1. Document Purpose

This specification defines the final status logic for the Medical Appointment Scheduling layer inside the Medical App.

It is intended for the programmer designing and building the web app so the scheduling flow behaves consistently in the UI, backend, automations, and reporting.

This document defines:
	•	the visible statuses
	•	how each status is triggered
	•	who owns each action
	•	timer-based automation rules
	•	transition rules
	•	retest and no-show cycle logic
	•	recommended technical structure for implementation

⸻

2. Scope

This specification applies only to the medical appointment scheduling flow.

Included
	•	appointment creation
	•	PRO-linked scheduling
	•	applicant-PRO meeting confirmation
	•	appointment completion
	•	result monitoring
	•	result delay handling
	•	no-show handling
	•	retest decision and rescheduling
	•	admin force close

Excluded
	•	Typing Job statuses
	•	broader work order statuses
	•	payment/accounting statuses
	•	visa processing statuses outside the medical scheduling layer
	•	client communication wording/content design

3. Core Design Decisions

These are fixed design decisions for this version.

3.1 Visible statuses must stay limited

Only decision-relevant statuses should be visible as the primary appointment status.

3.2 Automation-first approach

Wherever practical, the system should update status automatically.

3.3 Assignment exists, but not as a main visible status

The appointment is scheduled with a PRO already mentioned.
That assignment must exist in the data model and event log, but it is not a primary visible status in the final status list.

3.4 QR-based meeting confirmation is the primary “In Process” trigger

Meeting confirmation should be driven by QR scan where possible.

3.5 Manual fallback is allowed, but must be logged

If QR is unavailable, the PRO may manually confirm the meeting. This must be audit-logged as fallback verification.

3.6 “Result Issued” is a visible pass outcome

In this system, the visible status Result Issued represents that the medical result has been issued and is treated as the successful outcome.

3.7 Retest is a manual business decision

Retest must not be automatically set by default parser logic in this version.
It must be set manually by CRM or Admin.

3.8 No-show creates a new cycle, not overwritten history

If the applicant does not attend, the old appointment cycle remains preserved and a new scheduling cycle may be created.

3.9 Retest reuses the same scheduling flow

Retest does not create a separate visible status family.
It creates a new appointment cycle under the same case and re-enters from Scheduled.

3.10 Every manual change must be auditable

Any manual action, hold, override, fallback, or special decision must be logged with actor, time, and reason where applicable.

6. Trigger & Timer Rules

6.1 Scheduled

Selected trigger: 1A

The system automatically sets status to Scheduled when a new appointment booking is created.

The scheduling action also stores the PRO reference in the appointment data.

⸻

6.2 In Process

Selected trigger: 3A

The PRO scans the applicant QR code to confirm the meeting at the center.

Manual fallback
If QR is unavailable, the system may allow the PRO to manually mark the meeting as confirmed.

This fallback must log:
	•	fallback used = true
	•	actor
	•	timestamp
	•	reason or note if required

⸻

6.3 Completed

Selected trigger: 4A

The PRO manually marks the appointment as Completed after the medical process is finished at the center.

⸻

6.4 Result Issued

Selected trigger: 5A

Automation reads the relevant email and sets status to Result Issued when the issued/pass result is confirmed.

This should be idempotent and must not write duplicate state changes if the same email is processed multiple times.

⸻

6.5 Awaiting Meeting

Selected trigger: 6A

If the appointment has not reached In Process by 5 minutes after the appointment time, the system automatically changes the status to Awaiting Meeting.

⸻

6.6 No Show

Selected trigger: 7A

If the appointment remains in Awaiting Meeting for 30 minutes, the system automatically changes the status to No Show.

CRM intervention rule
CRM may intervene before the 30-minute threshold is reached if they are in contact with the applicant or PRO and know the applicant is still coming.

This should not necessarily change the visible status immediately, but it must prevent the automatic no-show action until the hold is cleared or expires.

⸻

6.7 Result Delayed

Selected trigger: 8A

If no valid result has been parsed within 30 hours from Completed, the system automatically changes status to Result Delayed.

⸻

6.8 Retest Required

Selected trigger: 9A

CRM or Admin manually sets Retest Required after reviewing the situation and confirming another appointment is required.

This is not a default automatic parser outcome in this version.

⸻

6.9 Medical Failed

Selected trigger: 10A

Automation reads the email and updates the appointment to Medical Failed when a fail outcome is confirmed.

This should also be idempotent.

⸻

6.10 Closed (Admin Override)

Selected trigger: 11A

Admin manually closes the appointment flow using override permission.

This action must require:
	•	override reason
	•	actor
	•	timestamp

8. Transition Rules

Allowed transitions
	•	Scheduled → In Process
	•	Scheduled → Awaiting Meeting
	•	Scheduled → Closed (Admin Override)
	•	Awaiting Meeting → In Process
	•	Awaiting Meeting → No Show
	•	Awaiting Meeting → Closed (Admin Override)
	•	In Process → Completed
	•	In Process → Closed (Admin Override)
	•	Completed → Result Issued
	•	Completed → Result Delayed
	•	Completed → Retest Required
	•	Completed → Medical Failed
	•	Completed → Closed (Admin Override)
	•	Result Delayed → Result Issued
	•	Result Delayed → Retest Required
	•	Result Delayed → Medical Failed
	•	Result Delayed → Closed (Admin Override)
	•	Retest Required → Scheduled
for a new cycle under the same case
	•	No Show → Scheduled
for a new cycle under the same case

Disallowed direct transitions
	•	Scheduled → Completed
	•	Scheduled → Result Issued
	•	Scheduled → Result Delayed
	•	Scheduled → Medical Failed
	•	Awaiting Meeting → Completed
	•	Awaiting Meeting → Result Issued
	•	Awaiting Meeting → Medical Failed
	•	In Process → Result Issued
	•	In Process → Medical Failed
	•	No Show → Completed
	•	No Show → Result Issued
	•	No Show → Medical Failed
	•	Retest Required → Result Issued directly
	•	Retest Required → Medical Failed directly

Final states

These should be treated as final states for a cycle:
	•	Result Issued
	•	Medical Failed
	•	Closed (Admin Override)
	•	No Show
(final for that cycle, but may create a new cycle under same case)

9. Exception Handling Rules

9.1 Awaiting Meeting

This is an operational alert state.

It exists when:
	•	appointment time passed by 5 minutes
	•	meeting still not confirmed

This should push attention to the case.

⸻

9.2 No Show

No Show is used when the appointment remained unresolved after the defined waiting period.

It should not destroy the case or replace the old cycle.

It should remain historically visible for that cycle.

⸻

9.3 Result Delayed

This indicates that:
	•	appointment was completed
	•	no result was received within 30 hours

This status is an escalation state and should appear in follow-up dashboards or internal alerts.

⸻

9.4 Retest Required

This is a controlled business decision.

It should only be set by CRM or Admin after review.

It should not automatically appear just because a result was not received.

⸻

9.5 Medical Failed

This is a final negative outcome for that cycle.

It should be set only when the result parsing confirms failure.

⸻

9.6 Closed (Admin Override)

This exists for exceptional closure cases.

Examples may include:
	•	duplicate records
	•	intentionally stopped case
	•	administrative cleanup
	•	business-directed closure

Override reason must be mandatory.

⸻

10. Retest Logic

Retest must be handled as a new appointment cycle under the same overall medical case.

Fixed rules
	•	Retest Required is a manual decision
	•	retest does not create a separate visible status family
	•	retest re-enters the same flow from Scheduled
	•	previous cycle remains preserved

Recommended retest sequence
	1.	Existing cycle reaches Retest Required
	2.	User creates a new appointment cycle
	3.	New cycle is marked with cycle_type = retest
	4.	New cycle starts again from Scheduled
	5.	Same flow repeats:
	•	Scheduled
	•	In Process
	•	Completed
	•	Result Issued / Medical Failed / Result Delayed

⸻

11. Reschedule / No-Show Cycle Logic

No Show must not overwrite the original appointment.

Required behavior
	•	old appointment cycle remains stored as No Show
	•	case remains open
	•	user may create a new appointment cycle
	•	new cycle starts from Scheduled
	•	both cycles remain linked to the same case

Same principle applies to regular rescheduling

If an appointment is moved after an earlier attempt fails operationally, the new booking should be treated as a new cycle/attempt rather than rewriting history.

12. Visibility Rules

Internal users

Internal operations, CRM, and Admin may see the full internal status list depending on permissions.

PRO visibility

Recommended PRO-visible statuses:
	•	Scheduled
	•	Awaiting Meeting
	•	In Process
	•	Completed

PRO does not need to see all internal result-monitoring states in V1.

Client-facing visibility

Client-facing visibility should be handled separately later if needed.

Do not directly expose the full internal status list to clients in V1 unless a simplified client-status layer is designed.

13. Recommended Data Model

This is the recommended structure for clean implementation.

13.1 Medical Case

Represents the overall medical matter for one applicant within the broader business context.

Example fields:
	•	case_id
	•	applicant_id
	•	work_order_id
	•	company_id
	•	overall_case_status
	•	created_at

⸻

13.2 Appointment Cycle

Represents one specific attempt or cycle within the case.

This can be:
	•	initial booking
	•	rescheduled booking
	•	retest booking

Example fields:
	•	appointment_cycle_id
	•	case_id
	•	cycle_number
	•	cycle_type (initial, reschedule, retest)
	•	appointment_time
	•	assigned_pro_id
	•	center_id
	•	current_status
	•	final_outcome
	•	created_at

⸻

13.3 Current Status

Each appointment cycle should have exactly one current visible status at a time.

This is the status shown in operational UI.

⸻

13.4 Event Timeline

This is important.

Not everything should become a visible status. Some items are better stored as events.

Recommended events:
	•	appointment created
	•	PRO assigned
	•	PRO changed
	•	QR scanned
	•	manual fallback used
	•	completed marked
	•	parser detected result issued
	•	parser detected fail
	•	CRM no-show hold placed
	•	CRM no-show hold removed
	•	retest decision entered
	•	new reschedule cycle created
	•	admin override executed

⸻

13.5 Outcome Fields

Status and outcome should not be treated as the same thing internally.

Recommended outcome examples:
	•	PASS
	•	FAIL
	•	NO_SHOW
	•	RETEST_REQUIRED
	•	OVERRIDDEN
	•	PENDING

This gives stronger reporting and cleaner analytics later.

15. Audit Log Requirements

The system must log all meaningful state changes and protected actions.

Minimum log requirements
	•	old status
	•	new status
	•	actor
	•	source
	•	timestamp

Mandatory-reason actions

The following actions must require a reason or note:
	•	manual fallback instead of QR
	•	CRM no-show hold
	•	Retest Required
	•	Closed (Admin Override)

Recommended audit extras
	•	related cycle id
	•	related case id
	•	parser source reference
	•	automation job identifier
	•	previous value and new value for key protected fields

16. Automation / Integration Notes

Email parsing

Email automation should support:
	•	pass/issued detection → Result Issued
	•	fail detection → Medical Failed

QR integration

QR should be the primary meeting confirmation method.

Manual fallback

Manual fallback must exist but be separately logged.

Idempotency

Automation must be idempotent.

That means:
	•	the same email should not produce duplicate status updates
	•	the same parser event should not create repeated timeline entries unless intentionally allowed

Timers / jobs

Background jobs should handle:
	•	Awaiting Meeting check
	•	No Show auto-escalation
	•	Result Delayed timer

Assignment handling

PRO assignment should still be stored as structured data and timeline event even though it is not a visible status.

17. Final Locked Flow

Standard successful path

Scheduled → In Process → Completed → Result Issued

Real-time delay path

Scheduled → Awaiting Meeting → In Process → Completed

No-show path

Scheduled → Awaiting Meeting → No Show
then optionally create a new cycle:
No Show → Scheduled (new cycle)

Result delay path

Completed → Result Delayed → Result Issued
or
Completed → Result Delayed → Retest Required
or
Completed → Result Delayed → Medical Failed

Retest path

Retest Required → Scheduled (new retest cycle) → In Process → Completed → Result Issued / Medical Failed / Result Delayed

Admin path

Any permitted active state → Closed (Admin Override)

18. Build Notes / Implementation Notes
	1.	Do not add extra visible statuses unless approved later.
	2.	Do not convert operational events into status chips unnecessarily.
	3.	Keep PRO assignment as structured data and timeline event, not a primary visible status.
	4.	Model this with Medical Case + Appointment Cycle + Current Status + Event Timeline.
	5.	Do not overwrite old appointment attempts during no-show, reschedule, or retest.
	6.	Preserve historical cycles for analytics, audit, and operational review.
	7.	Keep status logic and outcome logic distinct internally even if the UI wording is simplified.
	8.	Ensure background automation jobs are safe to re-run.
	9.	Require audit trails for every manual exception path.
	10.	Build the system so a future client-facing simplified status layer can be added later without changing the internal logic.
