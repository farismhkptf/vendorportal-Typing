Required outcome:

### 4. Missing notification: admin approval queue

### 5. Missing notification: WO auto-completion

### 6. Missing notification: new work order created

Required outcome:

### 7. Missing notification: MEDICAL_FAILED

CRM is not notified.

### 8. Missing notification: NO_SHOW

CRM is not notified.

### 9. Dead email templates

### 10. Quick-login production security risk

Required outcome:

* production must not expose unsafe quick-login access
* do not rely only on `NODE_ENV`

## Required implementation approach

### A. Use an event-driven cleanup for notification fixes

Do **not** scatter notification calls randomly across services.

Instead, first inspect whether there is already a domain-event / notification architecture in place.

If there is one:

* extend it properly

If there is not:

* create the smallest clean event-driven pattern needed for these fixes

Goal:

* each important workflow transition emits one canonical event
* notification delivery subscribes to that event
* retries do not create duplicates
* logic stays testable

This is especially important for:

* vendor job ready for scheduling
* pending admin approval
* WO auto-completed
* WO created
* MEDICAL_FAILED
* NO_SHOW

### B. Add tests for every fix

Each fix must include the right level of protection:

* unit tests where logic is isolated
* integration tests where route / service behavior matters
* workflow tests where state transition + notification + side effect matter

Minimum negative-path coverage to add where relevant:

* invalid UUID input
* repeated completion attempts
* repeated event emission
* missing recipient
* timer-triggered no-show path
* production-disabled quick-login access
* idle-draft panel missing-data / empty-state behavior

### C. Preserve idempotency

For all event-based fixes, ensure repeated executions do not cause:

* duplicate ledger entries
* duplicate emails
* duplicate notifications
* duplicate state transitions

### D. Add observability

For each newly wired event / notification path, add structured logs that make diagnosis easy:

* event name
* entity type
* entity ID
* recipient role / count
* sent / skipped / failed result
* reason for skip if applicable
