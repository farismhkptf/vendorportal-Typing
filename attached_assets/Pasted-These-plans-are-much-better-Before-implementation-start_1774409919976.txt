These plans are much better. Before implementation starts, please tighten the following points:

1. Keep Service Request status and physical custody status clearly separate.
Do not let SR status become a second custody tracker.
A cleaner SR status model would be something like:
Draft, SentToVendor, AcceptedByVendor, InProgress, Completed, Cancelled
with custody tracked separately through physical_custody_status.

2. Do not use loose client_company text if the current app already has structured client/company records.
Reuse existing client/company linkage where possible.

3. Step auto-generation logic must be explicit.
Do not create generic steps blindly.
The created steps must depend on the selected attestation service / variant, e.g. UAE only vs Home Country + UAE.

4. Keep future re-quote flexibility in mind.
V1 does not need a full re-quote workflow, but the structure should not make later revision/versioning difficult.

5. Vendor visibility must stay strict.
Vendor should not see client contacts, internal notes not meant for vendor, or client-side pricing/discussion history.

6. On vendor job cards, use cost wording carefully.
Do not assume “estimated cost” is always the right label in all states.

7. Custody log currently requires ID photo for every handover.
Please review whether this should be mandatory for every direction, or whether name/contact/signature are always mandatory and ID photo is conditionally required for external counterparties.
If you keep ID photo mandatory everywhere, that is acceptable only if done intentionally.

8. For VendorToUs handover, please think carefully about proof.
At minimum our receiving person signs, but also capture the vendor-side handover person identity.
Confirm whether vendor-side signature should also be captured there for stronger proof.

9. PRO should be able to view the custody timeline relevant to their tasks, not only Admin/CRM.

10. One critical rule is missing from the plans:
If the person on the client side giving or receiving the document is not the normal authorized contact/coordinator/manager, the form must require “Approved By” information.
Please add this to custody schema and UI.

11. Please maintain live operational fields for:
- current custodian
- current responsible person
not only infer everything from the last custody log row.

12. Reconsider the PRO UX slightly:
ideally all custody actions should be available through a unified task queue, rather than splitting some actions into dashboard and some into SR detail only.

Please revise the three plans with these refinements before implementation starts.
