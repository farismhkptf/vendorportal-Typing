Replit-Ready Implementation Prompt

Medical Appointment Scheduling Status Algorithm

Build Specification for Programmer

Use this as the implementation instruction for the Medical App scheduling layer.

⸻

Prompt

Build the Medical Appointment Scheduling Status System for the Medical App using the following fixed rules.

This scheduling status system is separate from the Typing Job status system.
Do not merge them.

The goal is to create a clean, automation-first scheduling layer with:
	•	minimal visible statuses
	•	strong auditability
	•	timer-based automation
	•	QR-based meeting confirmation
	•	cycle-based history preservation
	•	retest and no-show handled as new cycles, not overwritten records

⸻

1. Core Architecture

Build this using the following structure:

A. Medical Case

Represents the overall medical matter for one applicant.

B. Appointment Cycle

Represents each appointment attempt under the same case.

A cycle can be:
	•	initial
	•	reschedule
	•	retest

C. Current Visible Status

Each appointment cycle must have exactly one current visible status.

D. Event Timeline

Store operational events separately from statuses.

Examples of events:
	•	appointment created
	•	PRO assigned
	•	PRO changed
	•	QR scanned
	•	manual fallback used
	•	completed marked
	•	CRM no-show hold set
	•	CRM no-show hold removed
	•	parser detected issued result
	•	parser detected fail result
	•	retest decision entered
	•	admin override executed

Important rule

Do not model this as one flat mutable appointment row only.
Use case + cycle + status + event timeline.

⸻

2. Fixed Visible Status List

The only approved visible statuses for this version are:
	1.	SCHEDULED
	2.	IN_PROCESS
	3.	COMPLETED
	4.	RESULT_ISSUED
	5.	AWAITING_MEETING
	6.	NO_SHOW
	7.	RESULT_DELAYED
	8.	RETEST_REQUIRED
	9.	MEDICAL_FAILED
	10.	CLOSED_ADMIN_OVERRIDE

Do not add more visible statuses unless explicitly approved later.

⸻

3. Hidden Logic / Non-Status Data

The following should exist as data fields and/or events, not as visible statuses:
	•	PRO assignment
	•	assignment updates
	•	driving to center
	•	QR scan event
	•	manual fallback verification
	•	CRM no-show intervention
	•	email parser processing state
	•	parser source references

In particular:
	•	Assigned exists as event/data
	•	it is not a main visible status chip

⸻

4. Fixed Trigger Rules

Implement these exact triggers.

4.1 SCHEDULED

Trigger code: 1A

Set SCHEDULED automatically when a booking is successfully created.

Also store:
	•	assigned PRO
	•	appointment time
	•	center
	•	case relation
	•	cycle type

⸻

4.2 IN_PROCESS

Trigger code: 3A

Primary trigger:
	•	PRO scans applicant QR code at the center

Fallback:
	•	allow manual fallback if QR is unavailable
	•	fallback must be separately audit-logged

Store:
	•	meeting confirmed at
	•	meeting confirmation method = qr or manual

⸻

4.3 COMPLETED

Trigger code: 4A

PRO manually marks the appointment as completed after the medical process is finished at the center.

Store:
	•	completed at
	•	completed by

⸻

4.4 RESULT_ISSUED

Trigger code: 5A

Automation parses email and sets the cycle to RESULT_ISSUED when issued/pass result is confirmed.

Important:
	•	in this system, visible RESULT_ISSUED means successful issued/pass outcome
	•	keep internal outcome field = PASS

⸻

4.5 AWAITING_MEETING

Trigger code: 6A

If the cycle is still SCHEDULED at:
	•	appointment time + 5 minutes

then automatically set status to AWAITING_MEETING.

⸻

4.6 NO_SHOW

Trigger code: 7A

If the cycle remains in AWAITING_MEETING for 30 minutes, automatically set status to NO_SHOW.

Exception:
	•	if CRM/Admin has placed a no-show hold/intervention, do not auto-mark no-show during the hold

⸻

4.7 RESULT_DELAYED

Trigger code: 8A

If the cycle remains without parsed result for 30 hours after COMPLETED, automatically set status to RESULT_DELAYED.

⸻

4.8 RETEST_REQUIRED

Trigger code: 9A

Only CRM or Admin can set RETEST_REQUIRED.

This is a manual decision.

Do not auto-set this in V1.

⸻

4.9 MEDICAL_FAILED

Trigger code: 10A

Automation parses email and sets status to MEDICAL_FAILED when fail result is confirmed.

Also store internal outcome field = FAIL.

⸻

4.10 CLOSED_ADMIN_OVERRIDE

Trigger code: 11A

Only Admin can set CLOSED_ADMIN_OVERRIDE.

This must require:
	•	reason
	•	actor
	•	timestamp

⸻

5. Transition Rules

Only allow these transitions.

Allowed
	•	SCHEDULED -> IN_PROCESS
	•	SCHEDULED -> AWAITING_MEETING
	•	SCHEDULED -> CLOSED_ADMIN_OVERRIDE
	•	AWAITING_MEETING -> IN_PROCESS
	•	AWAITING_MEETING -> NO_SHOW
	•	AWAITING_MEETING -> CLOSED_ADMIN_OVERRIDE
	•	IN_PROCESS -> COMPLETED
	•	IN_PROCESS -> CLOSED_ADMIN_OVERRIDE
	•	COMPLETED -> RESULT_ISSUED
	•	COMPLETED -> RESULT_DELAYED
	•	COMPLETED -> RETEST_REQUIRED
	•	COMPLETED -> MEDICAL_FAILED
	•	COMPLETED -> CLOSED_ADMIN_OVERRIDE
	•	RESULT_DELAYED -> RESULT_ISSUED
	•	RESULT_DELAYED -> RETEST_REQUIRED
	•	RESULT_DELAYED -> MEDICAL_FAILED
	•	RESULT_DELAYED -> CLOSED_ADMIN_OVERRIDE
	•	RETEST_REQUIRED -> SCHEDULED
only through creation of a new retest cycle
	•	NO_SHOW -> SCHEDULED
only through creation of a new reschedule cycle

Disallow

Do not allow invalid direct jumps like:
	•	SCHEDULED -> COMPLETED
	•	SCHEDULED -> RESULT_ISSUED
	•	IN_PROCESS -> RESULT_ISSUED
	•	AWAITING_MEETING -> COMPLETED
	•	NO_SHOW -> COMPLETED

⸻

6. Final-State Rules

Treat these as final for a cycle:
	•	RESULT_ISSUED
	•	MEDICAL_FAILED
	•	CLOSED_ADMIN_OVERRIDE
	•	NO_SHOW

Important:
	•	NO_SHOW is final for that cycle only
	•	the case remains open and a new cycle may be created

⸻

7. Retest and Reschedule Logic

7.1 No Show

When a cycle reaches NO_SHOW:
	•	preserve that cycle as historical
	•	do not overwrite it
	•	allow creation of a new cycle under the same case
	•	new cycle type = reschedule
	•	new cycle starts at SCHEDULED

7.2 Retest

When a cycle reaches RETEST_REQUIRED:
	•	preserve old cycle
	•	create a new cycle under the same case
	•	new cycle type = retest
	•	new cycle starts at SCHEDULED

7.3 Same Flow Reuse

The same visible status flow must be reused for:
	•	initial cycle
	•	reschedule cycle
	•	retest cycle

Do not create separate visible retest statuses.

9. Required Outcome Values

Keep status and final_outcome separate internally.

Suggested final_outcome values:
	•	PASS
	•	FAIL
	•	NO_SHOW
	•	RETEST_REQUIRED
	•	OVERRIDDEN
	•	PENDING

Examples:
	•	if status = RESULT_ISSUED, outcome = PASS
	•	if status = MEDICAL_FAILED, outcome = FAIL
	•	if status = NO_SHOW, outcome = NO_SHOW

10. Ownership / Permissions

System

Can set:
	•	SCHEDULED
	•	AWAITING_MEETING
	•	NO_SHOW
	•	RESULT_DELAYED

PRO

Can set:
	•	IN_PROCESS
	•	COMPLETED

CRM

Can:
	•	place/remove no-show hold
	•	set RETEST_REQUIRED

Admin

Can:
	•	place/remove no-show hold
	•	set RETEST_REQUIRED
	•	set CLOSED_ADMIN_OVERRIDE

Automation Parser

Can set:
	•	RESULT_ISSUED
	•	MEDICAL_FAILED

⸻

11. Background Jobs / Timers

Implement the following background automation jobs.

Meeting Delay Job

At appointment_time + 5 minutes:
	•	if current status = SCHEDULED
	•	set status = AWAITING_MEETING

No Show Job

At awaiting_meeting_started_at + 30 minutes:
	•	if current status = AWAITING_MEETING
	•	and crm_hold_no_show = false
	•	set status = NO_SHOW

Result Delay Job

At completed_at + 30 hours:
	•	if current status is still unresolved and no valid result parsed
	•	set status = RESULT_DELAYED

All background jobs must be safe to re-run.

⸻

12. Audit Rules

Audit every status change and protected action.

Each audit entry should store:
	•	old value
	•	new value
	•	actor
	•	source
	•	timestamp

Mandatory-reason actions:
	•	manual fallback instead of QR
	•	CRM no-show hold
	•	RETEST_REQUIRED
	•	CLOSED_ADMIN_OVERRIDE

⸻

13. UI Rules

Main appointment status chip

Show only the approved visible status.

Do not show these as main statuses
	•	Assigned
	•	Driving To
	•	QR Scanned
	•	Hold Placed
	•	Parser Running

These belong in the timeline/events area.

Recommended PRO-facing UI

PRO mainly sees:
	•	Scheduled
	•	Awaiting Meeting
	•	In Process
	•	Completed

Recommended internal admin/CRM UI

Admin/CRM can see:
	•	full visible status
	•	timers
	•	hold state
	•	event timeline
	•	cycle history

⸻

14. Implementation Constraints
	•	Do not overwrite old cycles
	•	Do not flatten reschedules and retests into the same mutable row
	•	Do not mix Typing Job status with scheduling status
	•	Do not let parser produce duplicate final transitions
	•	Do not create hidden state changes without timeline logging
	•	Do not expose extra visible statuses without approval

⸻

15. Expected Final Flow

Standard success

SCHEDULED -> IN_PROCESS -> COMPLETED -> RESULT_ISSUED

Meeting delay

SCHEDULED -> AWAITING_MEETING -> IN_PROCESS -> COMPLETED

No-show

SCHEDULED -> AWAITING_MEETING -> NO_SHOW
then new cycle:
SCHEDULED

Result delay

COMPLETED -> RESULT_DELAYED -> RESULT_ISSUED
or
COMPLETED -> RESULT_DELAYED -> RETEST_REQUIRED
or
COMPLETED -> RESULT_DELAYED -> MEDICAL_FAILED

Retest path

RETEST_REQUIRED -> new cycle -> SCHEDULED -> IN_PROCESS -> COMPLETED -> RESULT_ISSUED / MEDICAL_FAILED / RESULT_DELAYED

Admin path

active state -> CLOSED_ADMIN_OVERRIDE
